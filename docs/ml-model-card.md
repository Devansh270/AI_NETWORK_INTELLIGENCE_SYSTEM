## Model 1 — Congestion Predictor (XGBoost)

### Summary
Binary classifier (`xgboost-v1`) that predicts whether a 5-second traffic window is congested (1) or normal (0), based on a snapshot of flow-level features. Each window is classified independently — there is no temporal memory in this model (see Limitations).

### Inputs
| Feature | Description |
|---|---|
| `packet_rate` | Packets per second on observed flows |
| `avg_latency` | Average round-trip latency (ms) |
| `byte_rate` | Bytes per second |
| `flow_count` | Number of active TCP/UDP flows in the window |
| `tcp_ratio` | Fraction of traffic that is TCP (0.0–1.0) |

The full synthetic dataset also includes `udp_ratio` and `icmp_ratio` columns, but the trained model uses only the five features above.

### Output
| Field | Type | Description |
|---|---|---|
| `congestion_probability` | float (0–1) | Predicted probability of congestion |
| `prediction` | int (0/1) | Binary prediction at decision threshold |

**Decision threshold:** 0.5 (fixed — not yet tuned for false-positive/false-negative cost asymmetry)

### Training data
- **Source:** Synthetic, `ml/data/synthetic_traffic.csv`, generated by `ml/data/generator.py`
- **Sample size:** 12,000 rows
- **Train/test split:** 80/20, stratified
- **Class balance:** 70% normal, 30% congested

### Hyperparameters
Selected via 3-fold grid search optimizing F1 score.

| Parameter | Search space | Best value |
|---|---|---|
| `max_depth` | [3, 5, 7] | 3 |
| `learning_rate` | [0.05, 0.1, 0.2] | 0.05 |
| `n_estimators` | [100, 200] | 100 |
| `subsample` | [0.8, 1.0] | 0.8 |

### Evaluation metrics
Measured on the held-out 20% test set (2,400 samples: 1,680 normal, 720 congested).

| Metric | Score |
|---|---|
| Accuracy | 1.00 |
| Precision (congested) | 1.00 |
| Recall (congested) | 1.00 |
| F1 score (congested) | 1.00 |
| ROC-AUC | 1.00 |

**Confusion matrix / plots:** `ml/congestion/evaluation_plots.png`
**Raw metrics:** `ml/congestion/metrics.json`

**These scores are not a sign of a strong model — they're a sign of an easy dataset.** The synthetic generator produces non-overlapping feature ranges (e.g. normal traffic has `packet_rate` 10–300, congested has 400–2000), so a single linear threshold would also score 100%. This is documented and intentional at this stage; see Limitations.

### Serving
- **Endpoint:** `POST /predict/congestion`
- **Model file:** `backend/ml/congestion/model.joblib`
- **Scaler file:** `backend/ml/congestion/scaler.joblib`
- **Class:** `CongestionPredictor` (`backend/ml/congestion/predictor.py`)

**Measured inference latency:** ⚠️ **not yet validated.** A 30-request timing test returned ~2,066ms average on the first two calls, then a read timeout on the third. This is almost certainly the model/scaler being lazily loaded from disk on first request rather than cached at app startup, not genuine per-call inference cost — XGBoost inference on 5 features should be single-digit milliseconds. **Action item before Week 3 performance profiling (Day 17):** confirm `CongestionPredictor` is instantiated once at FastAPI startup (not per-request), then re-run the latency test. Until re-measured, do not quote a latency number in the presentation or resume.

### Known limitations
1. **Perfect test scores reflect the synthetic generator's clean class separation, not real-world predictive power.** Normal and congested ranges don't overlap in the training data, so the model hasn't been forced to learn a genuinely hard decision boundary. Expect a real accuracy drop on live or real-world traffic.
2. **No temporal modeling.** Each window is classified independently; congestion that builds gradually over multiple windows isn't captured by this model (this is what the LSTM is intended to address).
3. **Fixed 0.5 threshold**, not tuned for the actual cost of false positives vs. false negatives in this use case.
4. **12,000 training rows**, all synthetic — sufficient for this synthetic task but not representative of real network traffic distributions.
5. **Latency unconfirmed** — see Serving section above.

### Planned follow-up (from report.md recommendations)
- Add overlap to the synthetic generator's normal/congested ranges (e.g. `packet_rate` 250–450 overlap zone) and retrain to get a realistic difficulty level.
- Add borderline test cases (e.g. `packet_rate=350, tcp_ratio=0.7`) to the integration test suite and document what the model predicts.
- Compare against the LSTM anomaly detector on the same held-out test set once both are finalized.

## Model 2 — Anomaly Detector (PyTorch LSTM Autoencoder)

### Summary
Unsupervised LSTM autoencoder trained **only on normal traffic** (`congested == 0` rows). It learns to reconstruct normal sequences; at inference time, high reconstruction error on a new sequence indicates an anomaly.

### Inputs
| Feature | Description |
|---|---|
| `packet_rate` | Packets per second |
| `avg_latency` | Average latency (ms) |
| `byte_rate` | Bytes per second |
| `flow_count` | Active flow count |
| `tcp_ratio` | Fraction of traffic that is TCP |

**Sequence length:** 30 timesteps
**Features per timestep:** 5

### Output
| Field | Type | Description |
|---|---|---|
| `anomaly_score` | float (0–1) | Reconstruction error normalized against the threshold (`min(error / threshold, 1.0)`) |
| `reconstruction_error` | float | Raw mean squared reconstruction error |
| `is_anomaly` | bool | `error > ANOMALY_THRESHOLD` |
| `severity` | string | `"normal"` / `"warning"` / `"critical"` based on score bands |

**Configured thresholds (env-overridable):**
| Threshold | Value | Meaning |
|---|---|---|
| `ANOMALY_THRESHOLD` | 0.05 | Raw reconstruction error above which a window is flagged anomalous |
| `SEVERITY_WARNING_THRESHOLD` | 0.5 | Normalized score above which severity = "warning" |
| `SEVERITY_CRITICAL_THRESHOLD` | 0.8 | Normalized score above which severity = "critical" |

Note: the inference scheduler (`inference_scheduler.py`) uses a separate alert-firing threshold, `ANOMALY_ALERT_THRESH = 0.50`, on the normalized score — distinct from the predictor's own `ANOMALY_THRESHOLD` raw-error cutoff. Worth double-checking these two thresholds are intentionally different and not a leftover mismatch.

### Architecture
| Component | Detail |
|---|---|
| Encoder | 1-layer LSTM, hidden_size=64 |
| Decoder | 1-layer LSTM, hidden_size=64, fed the repeated final encoder hidden state across all 30 timesteps |
| Output layer | Linear(64 → 5) |
| Loss function | MSELoss |
| Optimizer | Adam, lr=1e-3 |
| Batch size | 32 |
| Max epochs | 50 |
| Early stopping | On validation loss, patience=7 |

### Training data
- **Source:** Same `synthetic_traffic.csv`, filtered to `congested == 0` rows only
- **Windowing:** Overlapping sliding windows of length 30 built from the normal subset
- **Train/val split:** 85/15 of generated sequences
- **Normalization:** `StandardScaler` fit on normal data only, saved to `scaler.joblib`

### Evaluation
⚠️ **Outstanding — not yet measured.** Need:
- Final training loss and final validation loss from the actual training run (re-run `python backend/ml/anomaly/train.py` and capture the last printed epoch line, or check if a training log was saved)
- Mean reconstruction error on a held-out set of normal samples vs. a held-out/synthetic set of anomalous samples, to confirm the 0.05 threshold actually separates the two populations meaningfully

Until these are filled in, the model card cannot claim the anomaly detector works as intended — only that it trains and serves without errors.

### Serving
- **Endpoint:** `POST /predict/anomaly`
- **Checkpoint file:** `backend/ml/anomaly/lstm_best.pt`
- **Scaler file:** `backend/ml/anomaly/scaler.joblib`
- **Class:** `AnomalyPredictor` (`backend/ml/anomaly/predictor.py`)
- **Input validation:** strictly requires exactly 30 timesteps × 5 features per request; raises `ValueError` otherwise
- **Measured inference latency:** ⚠️ not yet measured — run the same timing test used for the congestion endpoint, with a `{"window": [[...5 floats...]] * 30}` payload, once the cold-start issue above is resolved.

### Known limitations
1. Trained exclusively on synthetic normal traffic — no real anomalies (DDoS, scans, real congestion events) were used to validate that the model distinguishes meaningful anomalies vs. just unfamiliar-but-benign traffic.
2. Static threshold (0.05 raw error) — no drift detection if the definition of "normal" shifts over time.
3. Two separate threshold systems exist (predictor's `ANOMALY_THRESHOLD` vs. scheduler's `ANOMALY_ALERT_THRESH`) — confirm this dual-threshold design is intentional before the demo, since it's an easy point of confusion if asked about it live.
4. No quantitative separation evidence yet between normal and anomalous reconstruction error (see Evaluation).

## Combined inference pipeline

- Both models are invoked by the background scheduler in `app/services/inference_scheduler.py`.
- Congestion predictions and anomaly predictions are both written to PostgreSQL with `model_name`, `score`, and `binary_output`.
- Anomaly alerts fire when the normalized anomaly score exceeds `ANOMALY_ALERT_THRESH` (0.50); `auto_rule_manager.py` additionally reacts when anomaly score > 0.80, and treats `congestion_score < 0.30 and anomaly_score < 0.30` as a "clear" condition.
- **End-to-end pipeline latency:** ⚠️ not yet measured — check whether `inference_scheduler.py` logs per-cycle timing; if not, add a simple `time.time()` wrap around the scheduler's predict calls before Day 17 (Performance Profiling).
